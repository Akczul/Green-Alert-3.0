1 Planteamiento

Problema: los reportes ciudadanos de contaminación (agua, aire, residuos, ruido) suelen perderse entre canales informales, sin validación, seguimiento institucional ni análisis territorial. GreenAlert organiza esos reportes, su validación por moderadores y su atención por entidades, y los convierte en zonas de riesgo, historial e indicadores. La integración conecta el registro transaccional con cálculos ambientales y un historial analítico trazable, sin sustituir las pantallas ni las reglas existentes.

Justificación: el instructivo exige tres backends, cinco motores y tres mecanismos avanzados integrados a procesos reales (Jacanamijoy, 2026). Cada tecnología cumple una función verificable: transacción y autorización (Express/MySQL), cálculo paralelo (FastAPI/MongoDB), eventos inmutables e indicadores (Spring/Cassandra/Druid) y caché (Redis). Usuarios: ciudadanía, moderadores, entidades y administradores en dos niveles.

El objetivo es permitir que ciudadanía, moderadores, administradores y entidades consulten y gestionen información ambiental con permisos verificables. Se integraron cuatro desarrollos conservando sus historiales en una rama independiente. Esta entrega es local; no acredita publicación remota, instalación física móvil ni proveedores externos.

Objetivo verificableResultado esperado

O2 ContinuidadMantener contratos, sesiones revocables, reportes y reglas institucionales
O3 RecuperaciónCaché prescindible; hechos pendientes durables y reintentos idempotentes
O4 EntregaCódigo empaquetado, instalación reproducible, evidencia y artefactos móviles reales

Alcance: Express, FastAPI, Spring Boot, React y React Native; MySQL, MongoDB, Cassandra, Redis y Druid. No se añade ML. La regresión experimental heredada es opcional y no participa en la demostración integrada de riesgo.

La solución conserva límites explícitos: la aceptación con cuentas reales de Google y Microsoft y la instalación física de la APK se comprueban en la sustentación. Última integración: 15 comprobaciones correctas y 1 fallida por reconexión de Spring tras el cambio de IP de Cassandra.

CU01 Crear reporte

Actor: ciudadano autenticado. Precondición: sesión vigente y categoría activa. Flujo: completa título, dirección, ubicación y evidencias opcionales; Express valida; MySQL inserta el reporte y su hecho outbox; el sistema analiza y procesa evidencias, asigna atención cuando corresponde y responde 201. Alternativas: datos inválidos producen 400; fallo remoto conserva los límites de compensación documentados. Resultado: reporte pendiente y hecho durable.

CU02 Analizar riesgo

Actor: admin o moderador. Precondición: permiso vigente. Desde el dashboard solicita un período; Express selecciona exclusivamente reportes validados y minimiza datos; FastAPI calcula; MongoDB guarda el resultado. Alternativas: período inválido 400, exceso de snapshot 413, dependencia 503/504. Resultado: ejecución identificada y zonas calculadas.

CU03 Consultar historial e indicadores

Actor: propietario, entidad asignada o personal global según operación. Express comprueba el objeto en MySQL antes de consultar Spring. El administrador entrega pendientes y reconcilia el día UTC; Spring lee Cassandra, reemplaza el intervalo Druid y consulta agregados. Alternativas: objeto no autorizado 404, rol insuficiente 403, dependencia 503. Resultado: hechos o métricas, sin exponer tokens internos.

CU04 Gestionar usuarios por ámbito

Actor: superadministrador o administrador de ámbito con MFA. Precondición: sesión administrativa vigente. Flujo: abre /admin; el backend recarga su nivel y ámbito desde MySQL, lista solo usuarios de su ámbito y aplica el cambio de rol o estado en una transacción con auditoría. Alternativas: usuario fuera del ámbito 404/403; elevación por un administrador de ámbito 403; degradar al último superadministrador 409. Resultado: cambio auditado y sesiones del afectado revocadas.

CU05 Iniciar sesión con Microsoft

Actor: persona con cuenta Microsoft. Flujo: pulsa Microsoft; el backend genera state, nonce y PKCE; tras autorizar, valida el id_token (firma JWKS, emisor, audiencia, nonce), crea un ciudadano o usa el vínculo existente y redirige con un código temporal que la web canjea por cookies de sesión. Alternativas: state repetido 400, firma inválida 401, correo existente sin email_verified 409, administrador sin TOTP 403 hasta completar el segundo factor. Resultado: sesión web por cookies.

8 Operación y uso

Inicio limpio

npm.cmd run install:apps
npm.cmd run setup:integracion
npm.cmd run infra:final:config
npm.cmd run infra:final:up
# Abrir https://localhost:8443 (certificado de laboratorio)
npm.cmd run infra:final:superadmin -- correo@dominio

Node 24, Git y Docker Compose con contenedores Linux. Reservar unos 8 GB para Docker y memoria adicional para el host. La primera construcción y el arranque de Cassandra/Druid pueden tardar varios minutos. setup genera secretos locales y conserva valores anteriores; nunca imprime credenciales.

Recorrido por rol

Ciudadano: registrar cuenta, acceder, crear reporte, consultar propios y cerrar sesión. Moderador: validar un reporte y calcular riesgo desde dashboard. Entidad: revisar asignaciones y actualizar su ciclo de atención. Superadministrador: inicializado por el operador, enrola MFA, inicia con TOTP, asigna administradores de ámbito, consulta la auditoría y ejecuta reconciliación. Administrador de ámbito: gestiona solo los usuarios de su comunidad u organización. Usuario común que intenta abrir /admin o la API administrativa: recibe 403.

npm.cmd run test:integracion
# Runner con proyecto, red, credenciales y datos sintéticos propios

No ejecutar el bootstrap completo ni la cadena histórica sobre datos existentes. No usar down --volumes para detener una instalación que debe conservarse.

9 Identidad y autorización

Actor actualPuedeRestricción
ciudadanoCrear reportes y consultar su historialNo administra ni consulta historial privado ajeno
entidadConsultar y atender reportes asignadosNo accede a otro ámbito institucional
moderadorValidar reportes, analizar riesgo e indicadoresNo ejecuta operaciones de operador exclusivas admin
admin global (superadministrador)Administradores, niveles y ámbitos; categorías (parámetros); eventos y caché; auditoría. MFA obligatoriaNo borra auditoría; no cambia su propio rol; no deja el sistema sin superadministrador
admin de ámbito (segundo nivel)Usuarios comunes de su comunidad u organización. MFA obligatoriaNo se eleva ni eleva a otros; no ve ni modifica otro ámbito (403/404)

La fuente autoritativa de cada petición valida usuario activo, auth_version, sid, rol y entidad. Logout revoca la familia; cambiar privilegios invalida accesos antiguos según el contrato de seguridad. Los tokens internos no representan al usuario: Express debe autorizar antes de llamar al servicio.

La MFA usa un secreto por administrador cifrado con una clave separada del JWT. Un contador aceptado no puede reutilizarse; la actualización condicional MySQL cierra la carrera entre dos logins. El enrolamiento no se publica en la API y no reemplaza factores existentes. La custodia del material privado corresponde al operador y al titular del factor.

El inicio federado usa OpenID Connect sobre OAuth 2.0: el proveedor autentica y GreenAlert autoriza (OpenID Foundation, s. f.). Proveedores OIDC: Google (id_token verificado) y Microsoft Entra ID (Authorization Code + PKCE S256, state y nonce de un solo uso, firma RS256 con JWKS, iss, aud y exp). El rol se asigna en GreenAlert; un correo existente solo se vincula con email_verified. Una cuenta federada administradora completa el TOTP antes de recibir sesión. Facebook OAuth no se presenta como OIDC. El login con cuentas reales requiere registrar las aplicaciones en cada proveedor.

El primer superadministrador se crea por inicialización controlada (scripts/crear-superadmin.mjs), nunca por registro público. Los cuatro roles existentes se conservan: la jerarquía se expresa como nivel del rol admin para no romper contratos web ni móviles.

10 Integridad y rendimiento

MySQL conserva relaciones y unicidad; la inscripción simultánea devuelve una creación y un conflicto 409. La fila de reporte y su hecho outbox se confirman juntos mediante trigger. El worker no borra entregas fallidas y serializa workers por esquema, con cuatro peticiones de salida en paralelo.

Cassandra decide la identidad global mediante IF NOT EXISTS. Un reintento con mismo ID/contenido no agrega un hecho; el contenido diferente entra en conflicto. La proyección Druid reemplaza el intervalo diario en lugar de sumar un replay, y se consulta después de la disponibilidad del segmento.

Redis es una optimización: un miss, timeout o reinicio provoca lectura desde MySQL. La generación forma parte de la clave y se incrementa en la transacción de modificación, incluso cuando Redis está caído. El TTL limita residuos de revisiones previas sin eliminar claves ajenas.

La primera compilación Android y el stack consumen recursos compartidos, por lo que estas cifras no caracterizan una capacidad productiva.

No existe atomicidad distribuida entre cinco motores, ni rollback garantizado de almacenamiento externo. La auditoría HTTP y la mutación tienen una ventana de crash; los hechos de reportes sí quedan en outbox transaccional.
